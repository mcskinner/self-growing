# Control plane and agency

Status: ideas from the journal; not a newly implemented control-plane feature.

## What guides growth?

The [journal](sources/self-growing-journal.md) suggests goals, a mission statement, review steps that check changes against them, and even a builder persona: not only “what do you want to build?” but “who do you want to build it?”

These address different questions:

- Goals describe desired outcomes.
- Review practices assess whether changes serve those outcomes.
- A persona can shape collaboration and taste.
- Permissions and execution boundaries determine what actions are actually possible.

[Pluggable project principles](pluggable-principles.md) are a possible lightweight part of this space: reusable guidance that users can select, customize, or skip entirely. No project should have to adopt the recommended process merely to use the starter.

A persona or mission statement is not an execution sandbox. Treating those as interchangeable would confuse behavioral guidance with security.

## Personal tool versus public experiment

The working project is trusted, local-only software. Pi can execute commands with the owner's permissions; browser request protections are not a sandbox. See the [project limitations](../../README.md#intentionally-limited).

The journal also imagines an art-project extreme where anyone visiting could modify live software. That is a distinct speculative scenario. Vandalism, conflicting intentions, and authority become central; current local-app assumptions would not make public modification safe. This idea does not authorize exposing the existing app publicly.

## Tensions

Too little guidance leaves each change disconnected from intent. Too much guidance can freeze the tool or import a project-management bureaucracy into a small personal app. A [minimal core](minimal-core-and-workshop.md) lets richer governance remain an optional direction until its value is demonstrated.

## Questions

Who may propose, execute, review, or undo changes? How does an owner express preferences without writing a rigid specification? Which decisions should remain human? Can a workflow's values travel with an [adaptation](adaptations-and-capability-exchange.md), and which should remain local?

The [collective-learning](collective-learning.md) idea raises a separate authority boundary: a shared suggestion is not permission to change a recipient's app.
